## 一、要解决的问题

横截面回归阶段存在三个结构性隐患，都不是算法错误，而是工程组织问题：

1. **同一套口径存在两份实现。** 北交所新旧代码映射在
   `代码/monthly_rlm_ep.py` 和 `代码/bse_code_mapping.py` 里各写一份，切换日期
   `2025-09-30`、`2025-10-09` 和映射对数 `242` 也都硬编码。
2. **OLS 与 RLM 的口径不可比。** 两者各自实现前瞻收益：OLS 用「每月第一个交易日
   调仓 + 日收益复合」，RLM 用「每月最后一个交易日形成 + 次月首个交易日建仓 +
   复权收盘价端点相除」；规模控制变量一个来自外部规模因子文件，一个在脚本内用
   `ln(me_total)` 现算；最小样本数一个 100、一个 500。结果是一边 68 个月、另一边
   64 个月，EP 年度平均溢价在 2020、2021、2022 三年连正负号都不一致。
3. **报告与计算焊在一起。** 回归脚本里嵌了约 120 行 Markdown 报告生成，其中的
   文字性结论是硬编码的，数字变了不会跟着变。

## 二、这次做了什么

### 2.1 新增共享模块 `代码/common/`

共享模块只提供可复用的数据准备函数，不执行业务阶段逻辑、不写结果文件。

| 模块 | 职责 | 原来散落在 |
|---|---|---|
| `paths.py` | 项目路径、数据源路径、回归共享常量 | 各脚本顶部重复定义 |
| `parquet_io.py` | 分片读取 parquet、扫描交易日历 | `read_selected_dates` / `read_batches_for_dates` / `read_market_dates` 三份 |
| `market.py` | 行情快照清洗、B 股剔除、北交所新旧代码映射 | RLM 脚本 + `bse_code_mapping.py` 两份 |
| `calendar.py` | 月度形成／建仓／退出日历 | RLM 脚本内 |
| `returns.py` | 前瞻收益 | OLS / RLM 各一份，口径还不同 |
| `panel.py` | 形成日面板、行业面板、回归面板、规模 Z 值 | RLM 脚本内 |

### 2.2 北交所切换日改为从数据推导

新增 `parquet_io.scan_market_index()`，一次扫描同时得到交易日历和代码切换位置：
旧代码（`43/83/87xxxx.BJ`）最后出现的交易日就是切换前最后交易日，其后第一个交易日
就是 `920xxx.BJ` 启用日，两者之差即为需要映射的新代码数量。实测结果：

```
切换前最后交易日 2025-09-30：旧代码 242 只，920 代码 35 只
切换后首个交易日 2025-10-09：旧代码 0 只，920 代码 277 只
推导出的映射对数 = 277 - 35 = 242
```

写死的三个常量因此被移除。保留的安全性检查没有减少：映射必须一一对应、映射目标
必须等于切换日新增的 920 代码、原始价格与复权价格都必须连续。

### 2.3 脚本改为调用共享模块

- `代码/monthly_rlm_ep.py`：重写为只负责估计方法和结果呈现，数据准备全部调用
  `common`。
- `代码/bse_code_mapping.py`：改为薄兼容层，内部调用
  `common.market.derive_bse_mapping`，使映射算法全项目只剩一份；`step1_样本筛选.py`
  无需改动，行为不变。
- `代码/monthly_ols_ep_size.py`：同步改写为同口径版本。**按使用者要求，OLS 这条线
  到此停止，不再做进一步推进和对照分析。**

### 2.4 两处小毛病顺手修掉

- `missing_reason` 原本用 `fillna("missing_entry_row")` 兜底，会把「不在前瞻收益
  面板中」的证券误报成「缺建仓行」。现在单独标记为 `not_in_return_panel`，审计表
  新增 `n_not_in_return_panel` 列。
- 收敛判定增加 `final_coef_delta`（最后一次迭代的参数最大变化量）作为收敛裕度记录，
  便于判断某个月是否卡在迭代上限边缘。

## 四、这次定下的口径

| 项目 | 决定 | 理由 |
|---|---|---|
| 前瞻收益 | **只保留端点口径**（建仓日复权收盘价 → 退出日复权收盘价） | 与实际调仓规则自洽：只在两个端点上交易，期间是否停牌不影响能否成交 |
| 停牌处理 | 建仓日或退出日停牌 → 收益置为缺失 | 与端点口径一致；逐条记录缺失原因 |
| 规模控制变量 | `ln(me_total)` 在「EP 有效且市值有效」的形成日 universe 内做横截面 Z 标准化 | 使所有回归脚本的设计矩阵完全一致，不再依赖外部规模因子文件 |
| 行业控制 | 截距 + K−1 个申万一级哑变量 | 与「K 个哑变量无截距」张成同一列空间，参数化不同但拟合等价 |
| 最小观测数 | 500 | 统一 OLS 与 RLM 的门槛 |
| 北交所映射 | 切换日从数据推导，映射对数从数据推导 | 数据刷新后不会因为写死的 242 而整条流程报错，安全性检查不减少 |

## 九、关于仓库结构

数据清洗、因子计算、回归分析分层放在不同脚本是合适的，这也是行业通行做法，
但前提是**共享的部分必须只有一份**。现在的分层是：

```
第 0 层  common/        共享底层：读数据、清洗行情、映射代码、算收益
第 1 层  数据清洗        step1 样本筛选 → step2 利润表 → step3 TTM → step4 点时间对齐
第 2 层  因子计算        step5 MAD 去极值 + Z 标准化 → 因子结果
第 3 层  回归分析        monthly_rlm_ep / monthly_ols_ep_size
第 4 层  呈现            plot_* 绘图脚本与文档生成
```

分层的收益是每一步可以单独重跑、单独验收；代价是每一层都要显式声明输入输出，
所以跨层的公共逻辑一定不能各写一份 —— 这正是这次要修的地方。

建议后续（尚未执行）按下面的结构整理，使仓库更易读、更易让别人接手：

```

├── README.md
├── config/paths.toml            # 数据源路径（本机路径用 paths.local.toml 覆盖）

├── 日志/

```
